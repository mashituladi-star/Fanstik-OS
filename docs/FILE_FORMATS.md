# Собственные форматы файлов Fanstik-OS

## Назначение

Fanstik-OS использует собственное семейство расширений **Fanstik File Formats (FFF)**. Оно нужно, чтобы приложения, ядро, драйверы, службы, пакеты и ресурсы системы имели узнаваемые типы файлов, не копирующие напрямую соглашения Windows или Linux.

Расширение показывает предполагаемое назначение файла. Оно **не доказывает**, что содержимое корректно или безопасно: загрузчики и системные службы обязаны проверять внутреннюю сигнатуру, версию формата, размеры, архитектуру, ABI и целостность данных.

## Принятое семейство расширений

| Расширение | Полное название | Назначение | Тип содержимого |
| --- | --- | --- | --- |
| `.fexe` | Fanstik Executable | Исполняемая пользовательская программа или приложение | Бинарный исполняемый файл |
| `.fkrn` | Fanstik Kernel Image | Образ ядра Fanstik-OS | Бинарный образ ядра |
| `.fmod` | Fanstik Module | Подключаемый программный модуль или библиотека | Бинарный модуль |
| `.fdrv` | Fanstik Driver | Драйвер устройства | Бинарный драйвер |
| `.fpkg` | Fanstik Package | Установочный пакет приложения или компонента | Архив пакета с метаданными |
| `.fsvc` | Fanstik Service Manifest | Описание системной службы | Текстовый манифест |
| `.fconf` | Fanstik Configuration | Конфигурация ОС или приложения | Текстовый конфигурационный файл |
| `.fres` | Fanstik Resource Bundle | Набор ресурсов приложения или системы | Контейнер ресурсов |
| `.fdisk` | Fanstik Disk Image | Образ виртуального или установочного диска | Образ диска |
| `.fsh` | Fanstik Shell Script | Скрипт командной оболочки Fanstik | Текстовый сценарий |

Расширения в таблице являются базовым набором FFF. Новые расширения добавляются только после описания их назначения и формата в этом документе.

## Назначение каждого формата

### Программы и системный код

- **`.fexe`** — обычные исполняемые приложения. Примеры: `Settings.fexe`, `Terminal.fexe`, `FileManager.fexe`. Формат должен описывать точку входа, целевую архитектуру, ABI, сегменты, зависимости и релокации.
- **`.fkrn`** — образ ядра. Пример: `FanstikKernel.fkrn`. Это отдельный тип образа с требованиями к загрузке, точке входа и передаваемой структуре boot-info.
- **`.fmod`** — подключаемые модули и библиотеки. Пример: `NetworkStack.fmod`. Для них будет определён отдельный ABI модулей и правила разрешения зависимостей.
- **`.fdrv`** — драйверы оборудования. Примеры: `NVMe.fdrv`, `USBHost.fdrv`, `Display.fdrv`. Драйвер должен объявлять поддерживаемый ABI, архитектуру и требуемые системные возможности. Само расширение не даёт драйверу права на загрузку.

### Установка, службы и данные

- **`.fpkg`** — пакет установки. Он содержит манифест пакета, версию, целевую архитектуру, зависимости, список файлов, контрольные суммы и, когда будет реализована инфраструктура доверия, цифровую подпись.
- **`.fsvc`** — манифест службы. Он описывает имя службы, исполняемый файл `.fexe`, параметры запуска, зависимости, политику перезапуска и необходимые разрешения. Манифест сам по себе не является исполняемым кодом.
- **`.fconf`** — текстовая конфигурация в UTF-8. Формат должен быть версионированным, читаемым человеком и иметь однозначные правила типов и значений.
- **`.fres`** — контейнер ресурсов: изображения, иконки, шрифты, локализация, звуки и другие данные. Контейнер ресурсов не должен исполнять находящийся внутри код.
- **`.fdisk`** — образ диска для виртуальной машины, тестирования или установки системы. На первом этапе он может представлять собой raw-образ с таблицей разделов GPT; отдельный контейнерный заголовок для него не считается реализованным.
- **`.fsh`** — текстовый сценарий для будущей командной оболочки Fanstik. Он интерпретируется оболочкой и не является нативным бинарным приложением.

## Предлагаемая структура бинарных форматов

Для бинарных форматов `.fexe`, `.fkrn`, `.fmod`, `.fdrv`, `.fpkg` и `.fres` будет определён общий набор правил:

1. **Magic signature** — уникальная сигнатура в начале файла. Нельзя определять тип бинарного файла только по расширению.
2. **Версия формата** — major/minor, чтобы изменять формат с контролем совместимости.
3. **Размер заголовка и файла** — все смещения и размеры проверяются до чтения данных.
4. **Целевая архитектура** — начальная целевая архитектура Fanstik-OS: x86_64.
5. **ABI version** — версия интерфейса, с которым должен взаимодействовать файл.
6. **Таблица секций/сегментов** — тип, смещение, размер, выравнивание и разрешения доступа.
7. **Целостность** — контрольная сумма содержимого; для пакетов и распространяемых системных компонентов позднее должна поддерживаться криптографическая подпись.

Точный двоичный layout, размеры полей, числовые коды, алгоритм хеширования, правила релокаций и подписи будут зафиксированы отдельной версией спецификации до реализации полноценных загрузчиков. Нельзя считать перечисленные общие правила уже готовым бинарным стандартом.

## UEFI и стандартное расширение .EFI

На x86_64 UEFI прошивка ожидает стандартное съёмное загрузочное приложение по пути `EFI/BOOT/BOOTX64.EFI`. Поэтому расширение **`.EFI` сохраняется для начального UEFI-загрузчика**: оно требуется средой прошивки и не является отказом от собственных форматов Fanstik.

После запуска собственного загрузчика проект сможет перейти к своим форматам ядра и приложений. Текущая сборка ещё создаёт `BOOTX64.EFI` и отдельный `kernel.elf`; загрузчик пока не загружает этот ELF и не передаёт ему управление. Формат `.fkrn` описан как целевой формат, но пока не реализован.

Это иллюстрация будущей организации файлов, а не описание уже существующей файловой системы.

## Безопасность и правила загрузки

- Запрещено доверять расширению без проверки сигнатуры и внутренней структуры файла.
- Все размеры, смещения, таблицы и арифметические операции проверяются на переполнение и выход за границы файла.
- Архитектура и ABI сверяются с текущей системой до загрузки.
- Драйверы и модули загружаются только после проверки подписи/политики доверия, когда такая инфраструктура будет реализована.
- Пакеты устанавливаются с проверкой манифеста, зависимостей и целостности; установка должна быть атомарной или иметь механизм отката.
- Файлы конфигурации и манифесты обрабатываются как недоверенный ввод.
- Повреждённый или неизвестный формат должен приводить к контролируемой ошибке, а не к исполнению данных.

## Статус реализации

На момент написания документа семейство FFF **спроектировано на уровне назначения расширений, но ещё не реализовано в загрузчике, ядре, файловой системе или менеджере пакетов**. Текущие артефакты сборки остаются `BOOTX64.EFI` и `kernel.elf`.

Следующие шаги:

- [ ] Утвердить и зафиксировать бинарную спецификацию FEXE/FKRN/FMOD/FDRV.
- [ ] Определить общий валидатор заголовков и проверок границ.
- [ ] Реализовать загрузку и проверку образа ядра.
- [ ] Определить формат манифестов `.fsvc` и конфигураций `.fconf`.
- [ ] Описать формат пакета `.fpkg`, его зависимости и контроль целостности.
- [ ] Добавить тестовые корректные, повреждённые и несовместимые файлы каждого бинарного типа.

Любое изменение утверждённого формата должно сопровождаться обновлением версии спецификации, тестов и этого документа.
