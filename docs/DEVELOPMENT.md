# Руководство разработчика

## Рабочий цикл

Изменения сначала проверяются host-side тестами, затем сборкой UEFI и ядра, а для загрузочных изменений дополнительно smoke-тестом в QEMU. Не отмечайте подсистему реализованной только по наличию исходного файла: результат должен быть проверяемым.

```sh
make clean all test
```

## Запуск в QEMU

Нужны `qemu-system-x86_64`, OVMF CODE и шаблон OVMF VARS:

```sh
OVMF_CODE=/usr/share/edk2/x64/OVMF_CODE.4m.fd \
OVMF_VARS=/usr/share/edk2/x64/OVMF_VARS.4m.fd make run
```

`make run` создаёт `build/esp.img` заново. Образ содержит `EFI/BOOT/BOOTX64.EFI` и `kernel.elf`, поэтому он также служит основой для будущего USB/live-потока.

## Границы кода

- `boot/uefi/` — UEFI ABI, чтение файлов, ELF-проверка и передача управления.
- `include/fanstik/` — ABI между загрузчиком и ядром, который нельзя менять без увеличения версии.
- `kernel/arch/x86_64/` — архитектурно-зависимый вход и низкоуровневые механизмы.
- `kernel/core/` — общая логика раннего ядра.
- `kernel/drivers/` — драйверы ранней диагностики и будущих устройств.
- `scripts/` — воспроизводимые инструменты создания образов и запуска эмулятора.
- `tests/` — host-side проверки, не являющиеся кодом, который выполняется внутри ОС.

## Правила загрузчика

Все размеры и смещения входных ELF-данных проверяются до разыменования. Фиксированный адрес сегмента сначала резервируется через `AllocatePages`. После успешного `ExitBootServices` нельзя вызывать Boot Services или освобождать их память. При изменении `boot_info` необходимо обновлять документацию и тесты ABI.

## Стиль и честность статуса

Исходный код и сообщения самой ОС остаются на английском, документация — на русском. Не скрывайте ошибки эмулятора и не заменяйте падение заглушкой. Если функция архитектурно подготовлена, но не работает end-to-end, указывайте это явно в `STATUS.md` и `ROADMAP.md`.
