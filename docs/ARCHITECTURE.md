# Обзор архитектуры

## Основные ограничения и решения

Fanstik-OS разрабатывается для компьютеров x86_64, загружаемых через UEFI. Legacy BIOS не поддерживается и не входит в планы. Операционная система реализуется самостоятельно: проект не использует ядро Linux и не наследует пользовательскую среду Linux.

Системный код пишется на C и Assembly в freestanding-режиме. Вспомогательные инструменты разработки и CI могут использовать shell и YAML.

## Язык проекта и язык документации

Исходный код, имена файлов и каталогов, идентификаторы, комментарии в исходниках, сообщения загрузчика и ядра, системный интерфейс и технические обозначения проекта — на английском языке.

Вся документация, включая этот документ, README, инструкции, архитектурные описания и дорожную карту, ведётся на русском языке. Названия API, инструкций процессора, регистров и форматов сохраняются на английском, если перевод может привести к неоднозначности.

## Приложение UEFI

Каталог `boot/uefi` содержит приложение UEFI x86_64 в формате PE/COFF. Прошивка передаёт управление функции `efi_main`, предоставляя дескриптор приложения и системную таблицу.

UEFI-приложение проверяет консоль, находит `kernel.elf` через Simple File System Protocol, проверяет ELF64 и загружает фиксированные `PT_LOAD`-сегменты по адресам линковки. До перехода к ядру загрузчик получает GOP, ACPI RSDP и финальную карту памяти, выделяет стек, вызывает `ExitBootServices` и передаёт указатель `boot_info` в `RDI`. Поддерживаются стандартный путь `EFI/BOOT/BOOTX64.EFI` и корневой `\kernel.elf` на ESP.

## Образ ядра

Каталог `kernel/` собирается в freestanding-образ ELF64, связанный по адресу `0x00200000`. Это начальная схема загрузки с идентичным отображением адресов. Сценарий компоновки разделяет исполняемые и доступные для записи сегменты.

Будущий загрузчик должен подготовить корректный стек, передать указатель на boot-info в регистре `RDI` и обеспечить отображение ядра по адресам, заданным при компоновке, прежде чем перейти к `_start`.

## ABI загрузочной информации

Файл `include/fanstik/boot_info.h` определяет версионируемую структуру данных для будущей передачи информации от UEFI-загрузчика ядру.

До появления собственной политики виртуальной памяти адреса в этой структуре считаются физическими. Нельзя менять порядок существующих полей без увеличения версии структуры или документированного плана совместимости.

## Собственные типы файлов Fanstik

Fanstik-OS использует придуманные имена расширений без буквенных сокращений с приставкой бренда. .vyrka — приложения, .orveth — ядро, .sylqen — модули, .drazik — драйверы, .qelvar — пакеты, .nethra — манифесты служб, .aunvek — конфигурации, .moryth — контейнеры ресурсов, .kavryn — образы дисков, .thavik — сценарии.

Для бинарных форматов будут определены внутренние сигнатуры, версии, архитектура, ABI, таблицы сегментов и проверки целостности. Точный двоичный layout будет определён отдельной спецификацией до реализации загрузчиков.

Начальный UEFI-файл сохраняет стандартное расширение .EFI и путь EFI/BOOT/BOOTX64.EFI, поскольку это точка входа UEFI-прошивки. На текущем этапе ядро по-прежнему собирается в kernel.elf; собственный тип .orveth пока является спецификацией, а не работающим загрузочным форматом.

Полный перечень типов, правила проверки и статус реализации приведены в [спецификации](FILE_FORMATS.md).

## Ранняя диагностика

Драйвер последовательного порта ядра использует COM1 с базовым адресом ввода-вывода `0x3F8`. Ожидание готовности передатчика ограничено по числу попыток, чтобы избежать бесконечного зависания.

Вывод через последовательный порт предназначен для журналов QEMU и ранней диагностики на реальном оборудовании.

## Границы подсистем

- `arch/x86_64`: GDT, IDT, обработчики исключений, точка входа ядра (реализовано).
- `mm`: распределитель физических страниц (PMM, реализовано), управление виртуальными адресными пространствами и kernel heap (планируются).
- `interrupts`: обработчики исключений (реализованы), маршрутизация PIC/APIC и источник таймера (планируются).
- `scheduler`: потоки, очереди готовых задач и переключение контекста (планируются).
- `syscall`: ABI системных вызовов и переходы между пользовательским и привилегированным режимами (планируются).
- `drivers`: консоль (серийный порт, реализовано), накопители, устройства ввода, перечисление PCI и таймеры (планируются).
- `fs`: VFS и начальная файловая система в памяти (планируются).
- `userspace`: процесс init, командная оболочка и системные утилиты (планируются).
- `graphics`: сначала консоль на framebuffer, позднее композитор и оконная система (планируются).

Реализовано помечено соответствующим образом; всё остальное — на будущих этапах.
