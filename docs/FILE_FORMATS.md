# Собственные типы файлов Fanstik-OS

## Почему придуманы новые имена

Fanstik-OS не использует расширения, построенные как очевидные буквенные сокращения с префиксом бренда. Вместо этого проект вводит отдельный набор придуманных имён типов файлов. Они не являются переименованием Windows/Linux форматов и не пытаются выглядеть как привычные системные суффиксы.

Названия выбраны как цельная лексика Fanstik. Они намеренно необычные и не выводятся напрямую из слов «executable», «kernel», «driver» и т. п. Их смысл закрепляется этой спецификацией.

Это авторские придуманные имена; глобальную уникальность во всех существующих проектах и доменах не гарантирует никакая подборка без отдельной проверки реестров и товарных знаков.

## Утверждённый набор расширений

| Расширение | Назначение | Содержимое |
| --- | --- | --- |
| .vyrka | Пользовательские приложения и исполняемые программы | Бинарный executable |
| .orveth | Образ ядра Fanstik-OS | Бинарный kernel image |
| .sylqen | Модули и библиотеки, подключаемые системой | Бинарный модуль |
| .drazik | Драйверы оборудования | Бинарный драйвер |
| .qelvar | Установочный пакет программ или системных компонентов | Контейнер пакета |
| .nethra | Описание системной службы | Текстовый манифест |
| .aunvek | Конфигурация системы или приложения | Текстовая конфигурация |
| .moryth | Контейнер ресурсов: изображения, иконки, шрифты, звук, локализация | Контейнер данных |
| .kavryn | Образ виртуального/установочного диска | Disk image |
| .thavik | Сценарий командной оболочки Fanstik | Текстовый скрипт |

Имена являются частью спецификации Fanstik. Не добавляй расширения по аналогии с другими ОС: сначала предложи имя, назначение, структуру и правила безопасности, затем включи его в этот документ.

## Подробности типов

### .vyrka — приложения

Нативные приложения, которые пользователь запускает из оболочки или графической среды. Примеры будущих файлов: Settings.vyrka, Terminal.vyrka, FileManager.vyrka. Спецификация должна включать архитектуру, ABI, точку входа, сегменты, зависимости и релокации.

### .orveth — ядро

Образ ядра, загружаемый собственным загрузчиком. Пример: FanstikCore.orveth. Формат должен описывать требования к загрузке, адреса, точку входа и ABI boot-info. Сейчас ядро всё ещё собирается как kernel.elf; собственный формат пока не реализован.

### .sylqen — модули и библиотеки

Подключаемые модули ядра или системные библиотеки, когда будет определена модель модулей и ABI. Пример: NetworkLayer.sylqen. Подключение должно проверять версию ABI, зависимости, права и целостность.

### .drazik — драйверы

Драйверы оборудования, например NVMe.drazik, USBHost.drazik, Display.drazik. Формат не означает автоматического доверия: драйверы должны быть проверены по политике безопасности, архитектуре, ABI и подписи, когда механизм подписи будет реализован.

### .qelvar — пакеты

Пакет установки приложения или компонента. Предполагаемый контейнер включает манифест, версию, целевую архитектуру, зависимости, список файлов, контрольные суммы и цифровую подпись после появления инфраструктуры доверия. Установка должна поддерживать проверку, атомарное применение и откат.

### .nethra — системные службы

Текстовый манифест службы: идентификатор, путь к приложению .vyrka, параметры, зависимости, правила запуска/перезапуска и необходимые разрешения. Это декларативные данные, а не исполняемый код.

### .aunvek — конфигурации

Текстовые конфигурации UTF-8, читаемые человеком, с чётко определёнными типами, синтаксисом, значениями по умолчанию и версиями. Конфигурация не должна исполнять код.

### .moryth — ресурсы

Контейнер изображений, иконок, шрифтов, локализаций, аудио и прочих ресурсов. Ресурсы должны храниться как данные и не исполняться как код.

### .kavryn — образы дисков

Образ для установки, эмуляции, тестирования или виртуальных машин. Начальная реализация может быть raw-образом с GPT. Отдельный контейнерный заголовок не считается существующим до разработки.

### .thavik — скрипты

Текстовые сценарии будущей командной оболочки Fanstik. Интерпретируются shell и не являются нативными бинарными приложениями.

## Общие правила будущих бинарных спецификаций

Для бинарных типов .vyrka, .orveth, .sylqen, .drazik, .qelvar и .moryth предстоит определить:

1. Уникальную внутреннюю сигнатуру (magic), которую нельзя выводить только из расширения.
2. Версию формата и правила совместимости.
3. Размер заголовка, общие размеры и безопасную проверку диапазонов.
4. Целевую архитектуру, начальная — x86_64.
5. ABI и его версию.
6. Таблицы сегментов/секций, типы, смещения, размеры, выравнивания и разрешения.
7. Контроль целостности, а для распространяемых системных компонентов — криптографическую подпись.

Точный layout, размеры полей, алгоритмы хеширования, правила релокаций и подписи должны быть отдельной спецификацией, прежде чем загрузчик начнёт принимать эти форматы. Названия расширений не означают, что внутренний стандарт уже реализован.

## UEFI — исключение на этапе загрузки

UEFI x86_64 ожидает стандартное приложение по пути EFI/BOOT/BOOTX64.EFI. Поэтому начальный загрузчик сохраняет расширение .EFI: его использует прошивка до запуска собственной среды Fanstik. Это техническое требование начального этапа, а не часть пользовательского семейства расширений.

В текущей версии UEFI-приложение загружает `kernel.elf` с FAT32 ESP и передаёт ему управление после проверки ELF64 и вызова `ExitBootServices`. Артефакты сборки остаются `BOOTX64.EFI` и `kernel.elf`; собственный формат `.orveth` пока не подключён.

## Безопасность

- Нельзя доверять типу файла только по расширению.
- Проверять сигнатуру, версию, размеры, смещения, таблицы и overflow до чтения/загрузки.
- Сверять архитектуру, ABI и разрешённые возможности.
- Драйверы и модули должны проходить политику доверия; в будущем — проверку цифровой подписи.
- Пакеты должны проверять манифест, зависимости, целостность, корректность путей и иметь безопасную установку/откат.
- Конфигурации и манифесты всегда считать недоверенными входными данными.
- Неизвестный или повреждённый формат отклонять контролируемо.

## Статус

Набор расширений утверждён как проектное решение и описан документально. Он **не реализован в загрузчике, ядре, файловой системе, shell или менеджере пакетов**. Текущие артефакты остаются BOOTX64.EFI и kernel.elf.
